Book Store QA Showcase

A small Playwright + TypeScript framework against the public demoqa Book Store. It combines UI tests (Page Object Model), API tests and data setup (JSON + SQLite) in one codebase. The goal is to show how I structure a suite and why. It is not meant to cover every feature.

Highlights

3 suites, one framework

API, Functional UI and End-to-end as separate Playwright projects, plus a @smoke subset across all three.

Parallel by default

fullyParallel: true. 19 tests in ~40 s locally, ~50 s in CI with 2 workers.

Independent tests

Each test creates its own user through the API and deletes it afterwards. No serial mode, no shared accounts, any test runs alone.

POM through fixtures

Private locators, user-level actions, expectX assertions. Specs contain no selectors.

Hybrid E2E

Arrange by API, act in the UI, assert in both the UI and the backend.

Data layer

JSON test data + SQLite: expected values and a ledger of created users for cleanup.

Proven stable

--repeat-each=3 → 57/57 green, 0 leftover users. Typecheck + format gates in CI.

Live results

Every push to main runs CI and publishes the HTML test report.

One-line design: use the API to arrange data, use the UI only for the behaviour under test, then assert on both the UI and the backend. Every test creates its own data and cleans it up, pass or fail.

Layers & dependencies

Architecture

Dependencies point one way: specs depend on fixtures, fixtures build everything else. A spec never creates a page object, an HTTP client or a DB connection itself.

tests/{api,ui,e2e}Specs. Arrange / Act / Assert in domain words. Get everything they need from fixtures.
▼ destructure fixtures
src/fixtures/index.tstest.extend: api, db (worker), testUser, signedInUser, page objects, ad-blocking context
▼ builds
src/pages/*UI. Private readonly locators, public actions and expectX assertions.
src/api/BookStoreClientHTTP. Typed wrapper over Playwright APIRequestContext. Same transport as the browser tests, no extra library.
src/db/TestDataDbData. SQLite with reference data and a ledger of created users. Parameterised SQL only.
▼ read by all
src/config · src/dataenv.ts validates env vars once. JSON files hold test data, typed in data/index.ts.

Test lifecycle

Architecture

What happens for a test that asks for signedInUser and profilePage:

globalSetup · once

Seed reference_books from JSON into SQLite.

worker

Open one TestDataDb per worker (WAL + busy timeout).

testUser

POST user → write ledger row → POST token.

signedInUser

Add 4 session cookies to the browser context.

test body

API arrange → UI act → UI + API assert.

teardown

Fresh token → DELETE user → mark ledger row deleted.

CI always()

npm run cleanup deletes any ledger row not marked deleted.

Fixtures are lazy. API tests never ask for page, so no browser starts for them.

Page Object Model

Coding style

BasePage only knows its path and how to open it. It deliberately has no shared helper methods: base classes that grow helpers turn into a dumping ground.

  • Locators are declared once, at the top, as class fields.
  • Parameterised locators are private methods: deleteIcon(isbn).
  • Actions read like user steps: login(), search(), deleteBook().
  • Assertions are named expectX and wrap web-first expect, so they retry.
  • Native dialogs are handled inside the page object, so specs don't need to know they exist.
BasePage.tsexport abstract class BasePage {
  protected abstract readonly path: string;

  constructor(protected readonly page: Page) {}

  async open(): Promise<void> {
    await this.page.goto(this.path);
  }
}
ProfilePage.tsexport class ProfilePage extends BasePage {
  protected readonly path = '/profile';

  private readonly userNameValue = this.page.locator('#userName-value');
  private readonly bookTitleLinks = this.page.locator('table tbody').getByRole('link');
  private readonly confirmOkButton = this.page
    .getByRole('dialog').getByRole('button', { name: 'OK' });

  private deleteIcon(isbn: string) {
    return this.page.locator(`#delete-record-${isbn}`);
  }

  async deleteBook(isbn: string): Promise<void> {
    // The app shows a native alert "Book deleted." after the modal.
    this.page.once('dialog', (dialog) => dialog.accept());
    await this.deleteIcon(isbn).click();
    await this.confirmOkButton.click();
  }

  async expectBookTitles(titles: string[]): Promise<void> {
    // list toHaveText = exact count + order, auto-retried
    await expect(this.bookTitleLinks).toHaveText(titles);
  }
}

src/fixtures/index.ts/** A fresh user per test, created by API (fast) and always deleted in teardown, pass or fail. */
testUser: async ({ api, db }, use) => {
  const credentials = newCredentials();
  const created = await api.createUser(credentials);
  db.recordUser({ ...credentials, userId: created.userID });     // ledger first: survives a crash
  const { token, expires } = await api.generateToken(credentials);

  await use({ ...credentials, userId: created.userID, token: token!, expires: expires! });

  // A UI login issues a new token and kills the old one, so never reuse it in teardown.
  const fresh = await api.generateToken(credentials);
  await api.deleteUser(created.userID, fresh.token!);
  db.markDeleted(credentials.userName);
},

/** The app reads its session from cookies, so we set them and skip the login UI. */
signedInUser: async ({ testUser, context }, use) => {
  const session = { userID: testUser.userId, userName: testUser.userName,
                    token: testUser.token, expires: testUser.expires };
  await context.addCookies(Object.entries(session).map(([name, value]) => ({ name, value, url: env.baseUrl })));
  await use(testUser);
},

// Override the built-in context (not an auto fixture) so API-only tests never start a browser.
context: async ({ context }, use) => {
  await context.route(THIRD_PARTY, (route) => route.abort());
  await use(context);
},

API client

Coding style

The client has two kinds of methods. The split is deliberate:

helper

createUser(), addBooks(), getUser()…

Parse the body and throw on an unexpected status, with URL and body in the message. Used for setup: if setup fails, the test should stop loudly instead of failing later somewhere confusing.

raw*

rawCreateUser(), rawGenerateToken()…

Return the APIResponse untouched. Used by API tests, which own their status and body assertions, including negative cases.

BookStoreClient.tsasync createUser(credentials: Credentials): Promise<CreatedUser> {
  return this.parse<CreatedUser>(
    await this.rawCreateUser(credentials), 201, 'create user');
}

private async parse<T>(response: APIResponse,
    expected: number, action: string): Promise<T> {
  if (response.status() !== expected) {
    throw new Error(
      `${action}: expected ${expected}, got ${response.status()} ` +
      `${response.url()}\n${await response.text()}`);
  }
  return (expected === 204 ? undefined : await response.json()) as T;
}
bookstore.api.spec.tstest('wrong password gets no token (200 + status Failed)',
  async ({ api, testUser }) => {
  // Quirk: 200 on failed auth. A status-only check would pass.
  const response = await api.rawGenerateToken({
    userName: testUser.userName, password: 'Wrong@1234' });

  expect(response.status()).toBe(200);
  expect(await response.json())
    .toMatchObject({ token: null, status: 'Failed' });
});

for (const { case: name, password } of data.passwordRules) {
  test(`weak password is rejected: ${name}`, async ({ api }) => {
    const response = await api.rawCreateUser({ ...newCredentials(), password });

    expect(response.status()).toBe(400);
    expect(await response.json()).toMatchObject({ code: '1300' });
  });

I used Playwright's own APIRequestContext rather than axios or supertest, so there is one dependency, one config (baseURL, timeouts), and API calls show up in the same trace and HTML report as UI steps.

TestDataDb.tsconstructor(path: string) {
  this.db = new Database(path);
  // Parallel workers share one file: WAL + busy timeout avoid "database is locked".
  this.db.pragma('journal_mode = WAL');
  this.db.pragma('busy_timeout = 5000');
  this.migrate();
}

listOrphans(prefix: string): LedgerUser[] {
  return this.db.prepare(
    `SELECT user_name AS userName, password, user_id AS userId
     FROM created_users WHERE deleted_at IS NULL AND user_name LIKE ? || '%'`,
  ).all(prefix) as LedgerUser[];             // parameterised, never string-concatenated
}

Why SQLite and not the app DB? demoqa is public and I have no DB access. SQLite stands in for the two DB roles a real suite has: a read-only source of expected values and a record of what the run created. TestDataDb is the seam. Swapping it for a read-only Postgres client keeps the same method names and the same parameterised queries.

Hybrid E2E test

Coding style

One test that shows the whole idea: API for speed, UI for behaviour, backend for truth.

tests/e2e/collection.e2e.spec.tstest('user removes a book from the profile', async ({ api, signedInUser, profilePage }) => {
  const [keep, remove] = data.referenceBooks;
  await api.addBooks(signedInUser.userId, signedInUser.token, [keep.isbn, remove.isbn]);  // Arrange: API, ~300 ms
  await profilePage.open();
  await profilePage.expectBookTitles([keep.title, remove.title]);                          // precondition visible

  await profilePage.deleteBook(remove.isbn);                                                // Act: the only UI step under test

  await profilePage.expectBookTitles([keep.title]);                                         // Assert: what the user sees
  // UI can lie (stale render, optimistic update). The API is the source of truth.
  await expect
    .poll(async () => (await api.getUser(signedInUser.userId, signedInUser.token)).books.map((b) => b.isbn))
    .toEqual([keep.isbn]);                                                                  // Assert: what persisted
});

Stability & CI

Quality

Flake controls

  • No fixed sleeps. List assertions (toHaveText([...])) retry until count and order match.
  • Third-party noise removed. Ad and tracker requests are aborted at the context level. They slowed pages and covered buttons.
  • Isolation. No shared accounts, so fullyParallel: true is safe.
  • Evidence. CI records a trace for every test, so the published report can be replayed step by step. Locally: trace and video kept on failure, screenshot on failure.
  • Retries only in CI (1), so flakiness shows up locally first.
  • Proof. --repeat-each=3 → 57/57, ledger shows 0 orphans.

Bug found in teardown

Real finding

First full run: 18 passed, 1 failed, and the failure was in teardown, not in the test.

delete user: expected 204, got 401 …/Account/v1/User/<id> {"code":"1200","message":"User not authorized!"}

Root causeThe UI login test signs in through the form. The server issues a new token and invalidates the one the fixture saved during setup. Teardown reused the old token.
Impact3 users stayed on the server (one per repeat). Without the ledger, nobody would have noticed until a shared environment filled up.
FixTeardown requests a fresh token right before DELETE. One line plus a comment explaining why.
Recoverynpm run cleanup found the 3 ledger rows with deleted_at IS NULL and deleted them.
LessonTeardown must not trust state the test may have changed. Record created data before any assertion, so cleanup still has a trail.

Strengths

Assessment

Fast

Setup through the API (~300 ms per user) instead of UI forms (5–10 s). 19 tests in about 40 s with parallel workers.

Isolated

Every test creates its own prefixed user. No order dependency, no shared accounts, no serial mode.

Self-cleaning

Fixture teardown on pass and fail, plus a DB ledger and cleanup script for killed runs. Verified: 0 orphans.

Readable

Specs are short, AAA-shaped, and free of selectors. Domain words like deleteBook, expectBookTitles.

Debuggable

Setup errors include status, URL and body. Traces include both API calls and UI steps in one timeline.

Checks the backend

The hybrid test confirms persistence through the API, not just what the page renders.

Catches API quirks

Assertions on response bodies, not only status codes (the 200 + "Failed" login case).

Data-driven without magic

Plain JSON, typed once. No Cucumber layer to maintain for a team of engineers.

Design FAQ

Assessment
Why not put assertions only in specs?

It is a valid style. I keep expectX in page objects because the locator and the assertion change together. Specs stay readable. When a spec needs a raw value for custom logic, the page object can expose a getter.

Why fixtures instead of beforeEach / afterEach?

Fixtures are lazy (only built when a test asks), composable (signedInUser builds on testUser), and pair setup with teardown in one place. Hooks run for every test in the file and spread setup and cleanup across two functions.

How would this scale to 500 tests and several teams?

Split fixtures by domain (fixtures/auth.ts, fixtures/books.ts) and merge them with mergeTests. Use one API client per bounded context. Shard in CI (--shard=1/4) and merge the reports. Keep tags for ownership and the PR gate.

How do you deal with a flaky test?

Reproduce with --repeat-each, then read the trace. Fix the cause, which is usually a missing wait condition, shared data or a third-party request. If it can't be fixed today, quarantine it with test.fixme and a ticket. I don't add retries to hide it.

Why Playwright's request context and not axios?

One dependency and one config. API calls appear in the same trace as UI steps, and the request fixture is already isolated per test.

What if the sign-up API is down?

Every test that needs a user fails fast in setup with a clear message (create user: expected 201, got 503 …), so the cause is obvious. The pure catalog test and the search UI tests still run, because they don't ask for a user.

How is this different from your production suites?

Production suites use the app's own seed/cleanup service and read-only DB checks, have much more domain logic, and deal with legacy UI frameworks. This repo keeps the same patterns in a form that fits on one screen.
